# PriceLab / Data Lake v2 — mini spec

# Scope

PriceLab v2 — локальная консольная утилита для подготовки непрерывного фьючерсного ряда из MT5 CSV.

В scope этой версии входит:
- поиск кандидатов на склейку по заданному алгоритму;
- вывод отчёта по найденным кандидатам;
- коррекция ряда по выбранным датам склеек;
- сохранение нового CSV в формате MT5 TSV.

В scope этой версии не входит:
- эвристический поиск склеек, скоринг склеек;
- автоматическое подтверждение найденных склеек без участия пользователя;
- работа с несколькими поставщиками данных;
- отдельная логика для квартальных и месячных фьючерсов;
- machine-readable report.

# Потребность

Для торговли фьючерсами на ММВБ используется MetaTrader 5.
Фьючерсные контракты имеют дату экспирации. При переходе на новый контракт цена обычно смещается относительно предыдущего. Для торговли это не является рыночным гэпом, но в исторических склейках брокера такой скачок часто присутствует как обычное ценовое движение.
При оптимизации стратегии на многолетнем периоде такие скачки искажают картину. Стратегия может начать подстраиваться под артефакты склейки, как будто это рыночный сигнал.

Мне нужна программа, которая:
- находит возможные склейки в имеющемся непрерывном ряду;
- показывает их пользователю;
- по выбранным датам устраняет ценовые разрывы;
- возвращает более чистый непрерывный ряд для дальнейших исследований.

# Идея

PriceLab v2 исходит из предположений:
1. Точки поиска задаются в конфиге и могут быть двух видов:
   - `day_change`
   - `fixed_time = HH:MM`
2. Разница между close предыдущей свечи и open следующей - это типичный разрыв. Как правило, типичный разрыв больше 0, и меньше 10 / 20 / 100 (свой у каждого символа)

Для каждой точки поиска программа:
- определяет `cur_bar` и `next_bar`;
- считает разрыв между `close` `cur_bar` и `open` `next_bar`;
- сравнивает его с типичным размером недавних межбаровых разрывов слева;
- если разрыв аномально велик, помечает дату как кандидата на склейку.

PriceLab v2 не принимает окончательное решение сам. Он предлагает кандидатов, а пользователь решает, какие из них использовать для коррекции.

# Terms

**search point** — правило, определяющее, где искать возможную склейку.
Поддерживаются:
- `day_change`
- `fixed_time = HH:MM`
**boundary** — конкретная пара соседних баров `cur_bar` и `next_bar`, выбранная по одному из search point.
**cur_bar** — бар, после которого проверяется возможный скачок.
**next_bar** — следующий бар после cur_bar, с которого может начаться скачок.
**signed_gap** — `next_bar.open - cur_bar.close`.
**gap_abs** — `abs(signed_gap)`.
**left_baseline** — типичный абсолютный межбаровый разрыв на заданном количестве свечей слева от `cur_bar`.
**roll candidate** — boundary, на котором найден аномально большой разрыв.
**confirmed roll** — кандидат, который пользователь выбрал для коррекции.

# User stories
## Detection
### US.1 Поиск дат склеек
Я, как пользователь, хочу чтобы PriceLab сам проверил точки поиска склейки и определил возможные roll_datetime.

### US.2 Просмотр параметров кандидата
Я, как пользователь, хочу видеть по каждой найденной дате величину разрыва и left_baseline, чтобы понять, похож ли этот случай на склейку.

### US.3 Настройка чувствительности
Я, как пользователь, хочу задать параметры поиска разрыва, чтобы настраивать чувствительность детектора под инструмент и таймфрейм.

### US.4 Настройка точек поиска склейки
Я, как пользователь, хочу задать возможные точки поиска склейки — стык дней или конкретное время, чтобы PriceLab проверял заданные мной точки возможной склейки.

## Adjust
### US.5 Коррекция склеек
Я, как пользователь, хочу чтобы PriceLab по выбранному списку дат устранил разрывы, чтобы получить плавный ценовой ряд.

# Inputs
## Quotes file

MT5 TSV / CSV с колонками:
- `<DATE>`
- `<TIME>`
- `<OPEN>`
- `<HIGH>`
- `<LOW>`
- `<CLOSE>`

Дополнительные колонки возможны, не должны влиять на логику, при Adjust должны сохраняться без изменений

## Param file

YAML / ENV файл с параметрами:

- `baselineDeep` — количество свечей слева для расчёта baseline; целое число > 0.
- `gapMultiplier` — множитель, определяющий, во сколько раз кандидат должен превышать left_baseline; число > 0.
- `searchPoints` — список точек поиска склейки.

Поддерживаемые значения `searchPoints`:
- `day_change` — искать склейку на границе между последним баром одного дня и первым баром следующего дня;
- `fixed_time = HH:MM` — искать склейку на boundary, где cur_bar имеет указанное время HH:MM

# Сценарии использования
## US.1 Поиск дат склеек
1. Пользователь запускает скрипт с указанием названия файла котировок
2. PL2 проверяет есть ли файл котировок, может ли его прочитать, соответствует ли он структуре
3. PL2 проверяет есть ли файл с параметрами, есть ли там `baselineDeep` и `gapMultiplier`, проверяет валидность значчений, читает из конфиг файла список `searchPoints`.
4. PL2 Открывает файл котировок и получает массив свечей и цен.
5. PL2 строит список candidate boundary по всем searchPoints.
6. PL2 двигается от самого позднего boundary к более ранним.
Для каждого search point:
- если search point = `day_change`:
  - `cur_bar` — последний бар дня `D`;
  - `next_bar` — первый следующий бар с датой `> D`.

- если search point = `fixed_time = HH:MM`:
  - `cur_bar` — бар с временем `HH:MM`.
  - `next_bar` — следующий бар в файле котировок;

- Если между `cur_bar` и `next_bar` календарно больше одного дня, это всё равно считается одним boundary, если в данных это соседние торговые участки.
7. Посчитать:
   - `signed_gap = next_bar.open - cur_bar.close`
   - `gap_abs = abs(signed_gap)`
8. Взять `baselineDeep` межбаровых переходов слева от cur_bar, не включая переход cur_bar -> next_bar. Если слева свечей меньше, чем `baselineDeep`, то boundary считается `few candles`.
9. Для этих свечей посчитать:
   - `left_baseline = median(abs(open[i] - close[i-1]))`
10. Если `left_baseline` получился равным 0, то взять `left_baseline = max(abs(open[i] - close[i-1]))`
11. Если max всё равно 0, то boundary считается `zero baseline`. Пользователь это увидит и проверит котировки вручную.
12. Если `gap_abs > left_baseline * gapMultiplier`, то datetime `next_bar` считается `roll_datetime`.
Это свеча, с которой начался скачок.
13. Когда необработанных boundary не осталось, считаем, что файл полностью проверен.
14. Формируем файл с датами. Для каждой даты печатаются:
- `roll_datetime`;
- `cur_close`;
- `next_open`;
- `signed_gap`;
- `gap_abs`;
- `left_baseline`;
- `threshold = left_baseline * gapMultiplier`.
- status `roll candidate` / `zero baseline` / `few candles`
Файл с датами в этом же виде должен быть пригоден для adjust
15. Показываем консольный отчёт: сколько найдено дат, сколько каких статусов.

## US.3 Настройка чувствительности
1. Пользователь открыл конфиг файл
2. Пользователь изменил значения
3. PL2 ничего про это не знает и никак не контролирует

## US.5 Коррекция склеек
1. Пользователь запускает скрипт с указанием названия файла котировок и файла с датами.
2. PL2 проверяет есть ли файл котировок, может ли его прочитать, соответствует ли он структуре.
3. PL2 проверяет есть ли файл с датами, есть ли там roll_datetime. 
4. PL2 проверяет есть ли дубликаты дат. Если они есть, PL2 предупреждает пользователя и не выполняет adjust.
5. Если с файлами всё норм, приступаем к обработке. PL2 не обращает внимание на другие данные, извлекает только roll_datetime. Остальные поля из файла check в adjustment не участвуют.
6. Пишем пользователю: сколько нашёл roll_datetime.
7. Обработка идёт от будущего к прошлому пока есть необработанные моменты склеек `roll_datetime`.
8. Берём самую свежую необработанную дату
9. Вычислили `signed_gap = next_bar.open - cur_bar.close`
10. Для всех баров с datetime `< roll_datetime` в полях `OPEN/HIGH/LOW/CLOSE`
  выполняется сдвиг:
   - `<OPEN>  := <OPEN>  + signed_gap`
   - `<HIGH>  := <HIGH>  + signed_gap`
   - `<LOW>   := <LOW>   + signed_gap`
   - `<CLOSE> := <CLOSE> + signed_gap`
Остальные поля не меняются.
11. roll_datetime считаем обработанным, берём следующий roll_datetime.
12. После обработки каждого roll_datetime уже внесённые изменения сохраняются и участвуют в следующих, более старых корректировках.
13. Факт обработки roll_datetime держим в памяти программы, не пишем в файл.
14. Запоминаем какие roll_datetime обработали и насколько сдвинули.
15. Новый CSV той же структуры и в том же формате MT5 TSV, к называнию добавляется "_rolled".
16. Как закончили обработку, пишем в консоль отчёт: какие roll_datetime обработаны, сколько их, как называется новый файл

# Требования к среде

PriceLab v2 рассчитан на локальный запуск в неизолированной Python-среде пользователя.

Требования:
1. Проект запускается без обязательного создания отдельного virtual environment.
2. Проект должен поддерживать запуск из VS Code при открытии корня проекта.
3. Для локального запуска в VS Code используется файл `.vscode/settings.json`, в котором `PYTHONPATH` указывает на папку `src`.
4. Пакет должен содержать `__main__.py`, чтобы команда запускалась в виде:
   `python -m pricelab ...`
5. Код проекта должен быть пригоден для запуска без установки пакета в систему, если `src` добавлен в `PYTHONPATH`.
6. Допустимо использовать распространённые сторонние библиотеки, например pandas и PyYAML.

## Перечень консольных команд и их примеры
CLI должен иметь две команды:
- `check` "python -m pricelab check --quotes rates\ALLFUTEu_M1_2025.csv --params rates\params.yaml".
- `adjust` "python -m pricelab adjust --quotes rates\ALLFUTEu_M1_2025.csv --rolls rates\ALLFUTEu_M1_2025_roll_candidates.csv".

## Пример .vscode/settings.json
{
  "terminal.integrated.env.windows": {
    "PYTHONPATH": "${workspaceFolder}\\src"
  }
}

# Правила (инварианты)

- Количество строк в output равно количеству строк в input.
- Порядок строк не меняется.
- Дата и время баров не меняются.
- Adjustment не изменяет ничего, кроме OHLC.
- Detection не меняет данные.
- Один и тот же confirmed roll не должен применяться дважды.
